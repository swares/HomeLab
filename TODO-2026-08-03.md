## ✅ Completed

### opi-zero2w-4 rebuild

- [x] **Root cause was storage geometry, not wifi.** The ext4 filesystem claimed
  15,204,352 4K blocks while its partition held 15,203,266 — the filesystem
  extended ~4.2 MB past the end of the card. Every boot wrote past usable space,
  corrupting config and leaving the journal dirty. That is why credentials and
  NetworkManager state were broken, and why `e2fsck` refused to run.
  Fixed by growing the image file 16 MB, replaying the journal, `resize2fs` down
  to the true partition size, then truncating back.

- [x] **Original SD card failed** — stopped enumerating entirely afterwards
  (`Get-CimInstance` / `Get-Disk` / Disk Management all blind to it while the
  reader itself was healthy). Replaced.

- [x] **Rebuilt on Orange Pi OS Debian Bookworm, BSP kernel 6.1.31.** The board
  had been on Orange Pi OS *Arch* (`Opios-arch-aarch64-xfce`), a rolling distro
  pinned to a frozen out-of-tree kernel, with a desktop stack on a headless node.

  Armbian is **not** an option for this board: it publishes only `current`
  (6.18.x) images, and the Zero 2W's **UNISOC UWE5622** wifi has no mainline
  driver. Verified by mounting the Armbian image — no `uwe5622`/`sprdwl_ng`
  modules, no `wcnmodem.bin`. Flashing it would have produced a board with no
  network and no ethernet port to recover through.

- [x] **Orange Pi's first-run mechanism is dead on arrival.**
  `orangepi-firstrun.service` already ran on Xunlong's build machine
  (`2024-07-11`) and removed its own enablement symlink, so
  `/boot/orangepi_first_run.txt` is never read on the user's first boot. Any
  headless preconfiguration must write the NetworkManager keyfile directly.

- [x] Board now `opi-zero2w-4` at `192.168.1.99` (matches inventory and Pi-hole
  client list), wifi surviving reboots, mosquitto HA-bridged to `opi-zero2w-2`,
  node-exporter and promtail restored **from playbooks, not the salvage tarball**.

- [x] **Wifi powersave disabled fleet-wide on the Zero 2W pool.** The UWE5622
  defaults to powersave on, parking the radio and dropping the first packet after
  idle — boards showed as intermittently unreachable in `lab-check`.
  `opi-zero2w-1/2/4` via NetworkManager; `opi-zero2w-3` runs netplan +
  systemd-networkd + wpa_supplicant (the odd one out) and got a oneshot unit plus
  a udev rule. Baked into `tools/sdcard/prep-armbian.sh` for future boards.

- [x] **SD card tooling committed** to `tools/sdcard/`. Windows cannot
  `wsl --mount` removable media, and standard imagers enumerate drive letters
  rather than physical disks, so these do raw `\\.\PHYSICALDRIVEn` access:
  `Inspect-SDCard.ps1`, `Dump-SDCard.ps1`, `Write-SDCard.ps1`, `prep-armbian.sh`,
  `diag-opi.sh`.
  `Write-SDCard.ps1` locks/dismounts volumes via FSCTL (`Set-Disk -IsOffline`
  does not work on removable media) and verifies by SHA256 readback.

### Monitoring — systemd collector finally works

- [x] **The 2026-07-26 diagnosis was wrong.** It concluded the collector could
  not work because node_exporter reads `/run/systemd/private` (root-only) — so
  the capability was written off and backup liveness moved to healthchecks.io.
  The pod log names a different path: it wants the D-Bus **system bus** at
  `/var/run/dbus/system_bus_socket`, which is `srw-rw-rw-`. No root needed.

  `runAsNonRoot` and read-only rootfs all retained).

  `node_systemd_timer_last_trigger_TIME_seconds` — no `_time` in the real name.

## 2026-08-04 — first failure caught by the new alerting

`lab-check` went red the morning after the alerting work, on the item the
alerting was added for. Worth recording that the whole chain worked: the failure
happened at 02:30, was visible at 15:10, and was root-caused the same day —

### ✅ Completed

- [x] **`lldap-backup` was installing restic at runtime.** The job ran
  `apk add --no-cache restic` inside `postgres:16-alpine` on every invocation, so
  each nightly backup depended on `dl-cdn.alpinelinux.org` being reachable over
  TLS at 02:30. On 04 Aug it was not:

      WARNING: fetching .../v3.24/main/aarch64/APKINDEX.tar.gz: TLS: unspecified error
      ERROR: unable to select packages:
        restic (no such package): required by: world[restic]

  restic was not missing from Alpine — the *package index* fetch failed, so apk
  had no catalogue. Exited non-zero twice, hit `backoffLimit` 64 seconds in, and
  that night's snapshot was lost. Not reproducible on a manual run hours later,
  because the CDN was reachable again by then.

  Split into two stock images with nothing fetched at runtime:
  `initContainer pg-dump` (`postgres:16-alpine`) →
  `container restic-backup` (`restic/restic:0.17.3`, verified on arm64), handing
  the dump over via an `emptyDir`.
  `gitops/workloads/lldap/backup-cronjob.yaml`
  *(PR `fix/lldap-backup-no-runtime-install`)*

  Side benefit: the content assertions (>1000 bytes, contains `CREATE TABLE`)
  now live in the init container, so a bad dump means the restic container never
  runs and cannot reach the repository. Previously only shell ordering prevented
  that.

- [x] **`restic snapshots --last 5` was silently wrong.** `--last` is deprecated
  and no longer takes a count, so the `5` parsed as a *snapshot ID*,
  prefix-matched `59a16050`, and printed one unrelated snapshot while ignoring
  `--tag`:

      Flag --last has been deprecated, use --latest 1
      Ignoring "filters": explicit snapshot ids are given

  The backup was fine; its own summary was lying. Now `--latest 5`. Note
  `--latest N` shows N *per group* (host+paths), so output stays longer than
  expected while multiple path-groups exist.

- [x] **Corrected the schedule comment** on the CronJob. It claimed the 02:30 job
  contends for the restic repo lock with the 01:30 `backup-nas` timer. Measured:
  `backup-nas` runs `01:30:00 → 01:30:14` nightly, so the windows do not overlap
  and there was no contention. The locks directory was also empty.

### 📋 Findings, not yet acted on

- **The restic repo is healthy.** 28 snapshots, `197,472 blobs / 203.482 GiB`,
  retention removing ~1 snapshot and 46 KiB nightly. The `nas` spacing (last 7
  dailies, weekly anchors at 19 and 26 July, monthly anchors in June) is exactly
  what `keep-daily/weekly/monthly` produces.

  ⚠️ A gap I "found" earlier was an artifact of running `restic snapshots
  --latest 3`, which truncates per group. Always list unfiltered before
  concluding anything about coverage.

- **`lldap` has missed two nights in three weeks**, from different causes:
  30 July (the job that hung 3d15h on NFS — now bounded by
  `activeDeadlineSeconds: 1800`) and 4 August (the apk failure above, now fixed).

- **`prune` runs without a cache** — `warning: running prune without a cache,
  this may be very slow!`. Finishing in seconds today, but it re-reads all
  indexes each run and will scale badly past 200 GiB. Usually means the unit runs
  with a `HOME` restic cannot write a cache into.

- **immich is dumping its database twice a night.** Your CronJob writes
  `immich-YYYY-MM-DD.sql.gz` at 01:30; Immich's own built-in backup writes
  `immich-db-backup-<ts>-v<ver>-pg<ver>.sql.gz` at 02:00. The built-in started
  around 26 July, so both have run for the last ~10 days. 53 files, 847 MB, with
  nothing pruning either set — and `backup-nas` snapshots the whole directory
  into restic nightly.

  Also: the CronJob's 01:30 slot collides with `backup-nas`, which includes
  `/mnt/cold-8t/immich` in its restic paths and ran `01:30:00–01:30:13` while the
  dump finished at `01:30:09` — so restic may capture a half-written `.sql.gz`.
  And unlike lldap, the immich dump has **no content assertion**, so an empty or
  truncated gzip would be backed up as a success.

  The CronJob also missed 1–2 July entirely, and the 3 July run happened at 16:46
  rather than 01:30 — i.e. manually triggered after someone noticed.

  Cleanest resolution is probably dropping the CronJob and keeping Immich's
  built-in, which has configurable retention — removing the collision, the
  unbounded growth and the redundancy at once. At the cost of trusting Immich's
  implementation over an asserted one.

- **`lldap-backup` init container failed once and self-healed** on the first test
  (`Init:0/1 → Init:Error → restart → PodInitializing`, all within 2 seconds).
  Logs were gone by the time we looked. If it recurs, Loki has it:
  `{namespace="lldap", container="pg-dump"}`. A retry loop around `pg_dump` would
  make it deterministic rather than relying on pod restart.

### 🔎 Loki access notes

Grafana Explore is the practical route: `https://grafana.apps.lab.home.arpa` →
Explore → Loki datasource. The two log sources are labelled differently:

  cluster pods    job="loki.source.kubernetes.pods"   namespace / pod / container
  non-cluster     job="journal"                       host / unit

So `{namespace="lldap"}` finds pod logs and `{host="opi-zero2w-4"}` finds a
board's systemd journal.

From the CLI, the parameter **must** be named — `--data-urlencode 'query={...}'`.
Omitting `query=` sends an unnamed parameter and Loki returns an empty result,
which looks exactly like "no logs were collected".

  that UI — they cannot be reviewed, version-controlled, or restored with the
  rest of the lab, which is the whole reason the GitOps CronJob wins. If the
  built-in is ever preferred, manage it declaratively via `IMMICH_CONFIG_FILE`
  rather than re-enabling it by hand.
- 14 leftover `immich-db-backup-*.sql.gz` files removed (227 MB). The CronJob's
  retention glob is deliberately strict (`immich-????-??-??.sql.gz`) so it will
  never touch the built-in's filenames — a bare `immich-*` would have.
- CronJob moved 01:30 → **01:00**, ahead of `backup-nas` at 01:30, plus atomic
  `.tmp` + `mv`, size assertion, `gzip -t`, a CREATE TABLE assertion, and 14-day
  retention. First real run: 24 dumps pruned, 16 retained.

**The bug worth remembering — `set -o pipefail` plus an early-exiting consumer.**
The content assertion was written `zcat "$TMP" | grep -q 'CREATE TABLE'`. That
is wrong in a way that only appears at scale: `grep -q` exits on the *first*
match, the decompressor is still writing ~208 MB, it takes SIGPIPE and exits
141, and `pipefail` promotes that to a failure of the whole pipeline. So a
**passing** check reported failure, and the job deleted a perfectly good dump.
Reproduced at the same scale — `grep -q` → rc=141, `grep -c` → passes. `grep -c`
reads the whole stream, so there is no early close. The same trap applies to the
`ls | head -20` line, which needs `|| true`.

Three days of dumps were lost to this before it was caught. Nothing at risk —
the failure path only ever removed `$TMP` — but the *backup was not running*
while the CronJob reported a clean, deliberate-looking error message.

**And a lesson about my own diagnosis:** after the `grep -q` fix was merged, jobs
kept failing, so I built two further theories (a missing `zcat`, then a mismatched
image) and had the user run probes against both. Both were wrong. The jobs that
kept failing were *pre-merge runs* — I never pinned the merge time against the job
timestamps, so I was explaining stale evidence with new hypotheses. Checking what
was actually deployed took one command and ended it immediately:

    kubectl -n immich get cronjob immich-db-backup \
      -o jsonpath='{.spec.jobTemplate.spec.template.spec.containers[0].args[0]}'

Establish *which version produced the failure* before theorising about why.

### 🔑 restic repository password exposed — ✅ ROTATED 2026-08-05 20:43 UTC

The password from `/etc/restic/password` was printed into a chat transcript on
08-05. Cause was a broken privilege boundary in a command intended to compare it
*without* disclosure:

    sudo tr -d '\n' < /etc/restic/password    # WRONG

The `<` redirection is performed by the calling shell, not by sudo, so the read
failed with permission denied, the left side of the `diff` was empty, and diff
printed the Vault copy in full as an addition. Correct form:

    sudo cat /etc/restic/password | tr -d '\n' | sha256sum

**Scope — two repos, both local:**

    /mnt/cold-8t/restic     primary       AFFECTED
    /mnt/cold-sec/restic    copy          AFFECTED
    s3:...r2.../homelab-backup   cloud    NOT affected — separate password,
                                          /etc/restic/cloud-password from
                                          secret/lab/cloudflare-r2

Rotation is cheap: a restic password protects the master key, not the data, so
this re-encrypts kilobytes rather than 203 GiB. `key add` / `key remove` is not
`forget`/`prune` and does not touch snapshots or retention.

    restic -r <repo> key list
    restic -r <repo> key add          # both repos
    # verify new password against BOTH before removing anything
    restic -r <repo> key remove <old-id>

Then update `/etc/restic/password`, `secret/lab/restic`, and the offline copy.
Confirm the lldap backup CronJob still runs afterward — it reads
`RESTIC_PASSWORD_FILE=/secrets/restic-password`, which comes from
`secret/lab/restic` via ESO, so a missed propagation surfaces at 02:30.

Note the `/etc/restic/password` file ends with a newline and the Vault copy does
not. Same password — restic trims it — but it means a `sha256sum` of the *file*
will not match a hash of the stored string. Compare trimmed values.

**Outcome.** Both repos now hold exactly one key:

    /mnt/cold-8t/restic   (4154928a)   44f892c5  created 20:43:01
    /mnt/cold-sec/restic  (34b4735f)   46108177  created 20:35:44

Removed: `87ff5770` and `4aead2b2` (the exposed June keys, one per repo) and
`75f20474` — a **stray third key** on the primary from a re-run of `key add` at

credential on the copy-of-record is a loose end even when it isn't a known

mistyped confirmation leaves a working key behind with no warning — always

## ✅ 2026-08-05 → 08-07 — Vault lockout and recovery (RESOLVED)

Revoking the exposed root token took its child tokens with it, locking us out of
Vault for ~40 hours. Recovered 08-07. Nothing was lost — Vault stayed unsealed
and held all its data throughout; what was lost was the ability to *authenticate*
to it. Every workload kept running, because `deletionPolicy: Retain` leaves
existing secrets in place when ESO cannot reach its backend.

**Final state:** no standing *root token* — `token-admin` (policy `admin`, 720h
TTL), `token-eso` and `token-vault-backup`, all three created with `-orphan` and
verified as `orphan=true`.

**Read that precisely.** It is not "no root-equivalent access". The `admin`
policy holds `create` plus `sudo` on `sys/policies/acl/*` and `auth/*`, so a
token carrying it can write a policy granting anything and mint a token for it —
escalating to root at will, without a key ceremony. Those capabilities are
deliberate; they are what let it run `vault auth enable kubernetes`.

So the gain from 08-05 was **removing a non-expiring credential that had leaked
into a transcript**, not eliminating root-equivalent access. That is still worth
having: the replacement expires, and has never been exposed. It just should not
be described as something stronger than it is. See the open item on tightening
`admin` if that trade stops being acceptable.

### What happened

The exposed init root token was revoked — objective met, and it cannot be undone.
But **revoking a token revokes its entire child tree**, and the admin token had
been created with plain `vault token create`, making it a child of the very token
being revoked. It died in the same instant. So did `token-eso`, created the same
way at some earlier date.

Result: zero valid tokens. `lookup-self` returns 403 for everything.

**The fix that should have been used, on every token, without exception:**

    vault token create -orphan -policy=admin -ttl=720h -display-name=token-admin
                       ^^^^^^^

`-orphan` detaches a token from its creator so that revoking the parent does not
cascade. This is documented Vault behaviour and was not accounted for when the
sequence was planned.

### Why `generate-root` was blocked — and the actual fix

`vault operator generate-root` returned 403 `permission denied` even with **no
token presented at all**, confirmed with bare curl so it was never a credential
problem:

    curl -s -X PUT http://127.0.0.1:8200/v1/sys/generate-root/attempt -d '{}'
    {"errors":["permission denied"]}

**This is HashiCorp Vault 2.0.3, not OpenBao.** The version number looks like
OpenBao's, the unit is `vault.service`, the binary is `/usr/bin/vault`, and the
package comes from `apt.releases.hashicorp.com`. HashiCorp Vault went 1.21 → 2.0;
`apt policy vault` shows the whole ladder. Hours were lost reading OpenBao
documentation — including a deprecation notice and a listener parameter,
`disable_unauthed_generate_root_endpoints`, that belong to a different product
and were correctly rejected as unknown fields.

The real cause is **CVE-2026-5807** (HCSEC-2026-08). An unauthenticated caller
could open and immediately cancel a root-generation or rekey operation in a loop,
permanently occupying the single in-progress slot and locking out real operators.
Vault 2.0 fixed it by requiring a **valid token in addition to key shares** on:

    sys/rekey
    sys/generate-root
    sys/replication/dr/secondary/generate-operation-token

Which is a bootstrapping trap: the endpoint that exists to recover lost root
access now requires a token you do not have.

**The escape hatch is a top-level parameter, and it is a string array:**

    enable_unauthenticated_access = ["generate-root"]

Supported families: `"rekey"`, `"generate-root"`, `"generate-operation-token"`.
Setting it to `true` fails to parse with `unknown slice type: *ast.LiteralType`
— which is a useful error, because it says "this wants a list" rather than
"unknown field".

It is **SIGHUP-updatable**, so removing it afterwards needs only
`systemctl reload vault` — no restart, no re-seal. Adding it does require a
restart if the process is already running.

Confirm the door is shut afterwards rather than assuming:

    curl -s -X PUT http://127.0.0.1:8200/v1/sys/generate-root/attempt -d '{}'
    # expect: permission denied

### Gotchas hit during the ceremony

- **The OTP and the encoded token must come from the same `-init`.** Cancelling
  and re-running `-init` issues a fresh OTP; pairing it with an encoded token
  from a previous attempt decodes to binary noise with no error. Bind them
  together instead:

      otp=$(vault operator generate-root -generate-otp)
      vault operator generate-root -init -otp="$otp"
      vault operator generate-root -nonce=<nonce>      # ×3, one share each
      vault operator generate-root -decode=<encoded> -otp="$otp"

- `vault operator generate-root -status` after completion shows
  `Started false / Progress 0/3`. That is normal — the attempt clears itself once
  it issues a token. It does not mean the ceremony failed.
- The CLI sends `~/.vault-token` automatically. A revoked cached token turns a
  clean `permission denied` into `permission denied + invalid token`, which reads
  like a different fault. Clear it before diagnosing:
  `unset VAULT_TOKEN; mv ~/.vault-token ~/.vault-token.bak`

### Config lives on the RPi5, not the H4

`/etc/vault.d/vault.hcl` on **192.168.1.128**. There is an unused `vault.hcl` and
`/usr/bin/vault` on the H4 as well — nothing runs it, its listener specifies TLS
while the live endpoint is plaintext HTTP, and that mismatch cost real time. It
is also a loaded gun: a stray `systemctl start vault` there would bind 8200 on
the NAS and answer as an empty Vault on the address the cluster trusts.

### Safety net — in place before stopping

    /mnt/cold-8t/vault-raft-2026-08-05.tgz    3.2M   cold copy of /opt/vault/data

Taken with Vault stopped, so it is consistent. It sits on the cold tier, so the
01:30 `backup-nas` run pulls it into restic automatically. **Everything below is
reversible because this exists.**

### Recovery as performed (08-07)

1. `enable_unauthenticated_access = ["generate-root"]` added top-level, restart,
   unseal.
2. `generate-root` ceremony with 3 of 5 shares → new root token.
3. Recreated every credential **with `-orphan`**: `token-admin` (policy `admin`,
   which survived — policies are not tokens), `token-eso`, `token-vault-backup`
   (policy `vault-snapshot`, written to `/etc/vault.d/backup-token`, `0600`,
   owned by `vault`).
4. ESO reads `tokenSecretRef` → secret `vault-token`, key `token`, namespace
   `external-secrets`. Updated in place, deployment restarted.
5. Store returned to `Valid`; all **16** ExternalSecrets `SecretSynced`.
6. `backup-vault` run manually — first success since 03 Aug, `hc-ping OK`.
7. Config line removed, `systemctl reload vault`, endpoint confirmed denying
   again, generated root revoked.

The raft tarball at `/mnt/cold-8t/vault-raft-2026-08-05.tgz` was never needed but
was the reason the recovery could be attempted without anxiety. Keep taking one
before this class of work.

**Final token inventory — three, all `orphan=true`:**

    token-token-admin          [admin default]            720h
    token-eso                  [default eso]              768h   <- in the cluster secret
    token-token-vault-backup   [default vault-snapshot]   768h   <- /etc/vault.d/backup-token

Note `-display-name=token-admin` renders as `token-token-admin`: Vault prefixes
`token-` for anything minted through `auth/token/create`. Pass `-display-name=admin`.

### `token-root-replacement` was never actually revoked on 08-05

It was still present on 08-07 — `[root]`, no expiry, created 29 June — and it
survived the cascade precisely because it was an orphan. The 08-05 notes recorded
it as revoked. It was not. Removed 08-07.

**`vault token revoke -accessor` prints `Success! Revoked token (if it existed)`
whether or not the accessor matched anything.** That message is not confirmation.
The only honest check is the count:

    vault list -format=json auth/token/accessors | jq 'length'

Related: do not address tokens by line number from an earlier listing. `vault
list` returns accessors in lexical order, unrelated to the order you read them
in, and the set changes as you mint and revoke. Match on `creation_time`, or use
the accessor explicitly.

### CLI gotcha that wasted time twice

`-accessor` is a **boolean** flag; the accessor is positional. Go stops parsing
flags at the first positional, so a trailing `-format=json` becomes a second
positional argument:

    vault token lookup -accessor <ACC> -format=json    # "expected 1, got 2"
    vault token lookup -format=json -accessor <ACC>    # correct

This produced the unexplained `Too many arguments` on 08-05 and again on 08-07.

### Pre-existing, not caused by the lockout

`backup-vault.service` had been failing since **04 Aug 02:33** — before any of
this — with `invalid token` against `sys/storage/raft/snapshot`. Its credential
was already dead, probably from the same July expiry that caused the ESO outage.
So Vault raft snapshots were missing from ~03 Aug until 08-07. Fixed in step 6.

**`backup-vault` failing is invisible unless something watches it.** It failed
silently for three days across two nightly runs. Worth an alert of its own.

### `vault-unseal.service`

A restart seals Vault, but `vault-unseal.service` restores it without manual
shares. Convenient, but it means unseal material is stored on the RPi5 — which
softens what a 3-of-5 Shamir split is meant to protect. Worth a decision later,
separate from this incident.

`backup-offsite` had never copied anything. `offsite_restic_repo` was defined

Two details that cannot be fixed later:

- The H4 runs **restic 0.12.1**, so the script takes the `--repo2` branch, not

### Alerting on backup *failure*, not just backup *silence*

`backup-vault.service` failed three nights running while `backup-vault.timer`
fired punctually at 02:30 each time. `LabBackupVaultSilent` watches
`node_systemd_timer_last_trigger_seconds` — the timer's last trigger — so it was
structurally incapable of noticing. **"Did it start?" and "did it work?" are
different questions.** Both rules are kept: a timer that stops firing produces no
failed state either.

`LabBackupNasFailed` (single unit, single host) is now `LabBackupUnitFailed`
across `backup-.+\.service` on all hosts.

**The collector regex was the real blocker.** It was
`--collector.systemd.unit-include=(backup-nas|backup-etcd)\.(service|timer)`, so
`backup-cloud`, `backup-verify` and `backup-offsite` produced **no series at
all** — no rule could have covered them however it was written. Widened to
`backup-.+\.(service|timer)`. Confirmed after sync:

    backup-cloud.service    backup-etcd.service    backup-nas.service
    backup-cloud.timer      backup-etcd.timer      backup-nas.timer
    backup-offsite.service  backup-verify.service  backup-verify.timer

(`backup-offsite.timer` is absent only because it is still disabled.)

Note the hosts differ: cluster nodes run the DaemonSet with that regex, while the
rpi5 runs the Debian `prometheus-node-exporter` package with `ARGS=""`, whose
systemd collector defaults to `unit-include=".+"`. That is why `backup-vault` was
visible to Prometheus while the H4's own `backup-cloud` was not.

**Argo reported `Synced` while serving a stale Helm render.** The `monitoring`
app's `status.sync.revision` is the *chart* version (72.6.2), not a git SHA — the
values live in `spec.source.helm.valuesObject` on the Application, owned by
`root`. `root` was at the right commit and the Application had the new regex, yet
the live DaemonSet still carried the old args. A **hard** refresh fixed it; a
normal refresh returns the cached render:

    kubectl -n argocd patch app monitoring --type merge \
      -p '{"metadata":{"annotations":{"argocd.argoproj.io/refresh":"hard"}}}'

### Proven end to end, deliberately

Rather than assume, a unit was made to fail on purpose:

    /etc/systemd/system/backup-alerttest.service  ->  ExecStart=/bin/false

Chain confirmed at every hop: metric exposed → rule `pending` → `firing` →
Alertmanager dispatched to `ntfy` and `m5stack` → **notification and resolution
both arrived on the phone**.

A first attempt with `systemd-run --unit=backup-alerttest /bin/false` failed to
prove anything: systemd reaped the transient unit before `for: 1m` elapsed, the
metric vanished, and the alert cleared. Use a real unit file for this test.

### Alertmanager routing, as it actually is

    route.receiver: "null"                     <- unreachable, see below
      Watchdog            -> watchdog
      InfoInhibitor       -> null
      severity=critical   -> ntfy      (continue: true)
      <no matchers>       -> m5stack   (catch-all)

The `null` default looks alarming but is never reached: the m5stack route has no
matchers and catches everything first. Nothing is silently dropped.

**But `severity=warning` reaches the M5Stack display only.** Four `KubeJobFailed`
alerts were firing, with zero silences, for days — they are `warning` in
kube-prometheus-stack, so they only ever appeared on a small screen. They were
stale leftovers from already-fixed failures (deleted 08-07).

**Resolved 08-07 with `LabBackupJobFailed`** at `severity: critical`, which the
existing route already sends to ntfy — no Alertmanager change, the intent lives
in the rule. Two details that matter:

- `kube_job_failed` (a Job *condition*), not `kube_job_status_failed` (a count
  of failed *pods*, nonzero for a Job that retried and then succeeded).
- Bounded to Jobs started within 24h. A failed Job persists until
  `failedJobsHistoryLimit` rotates it out, so an unbounded rule pages forever
  for a failure already handled — which is exactly how those four accumulated.
  Now it pages for the failure, not for the wreckage.

Scoped by `job_name=~".*backup.*"` so new backup CronJobs are covered on
creation, rather than by naming each one — the mistake that left
`LabVMUnexpectedShutoff` pointing at a VM decommissioned three weeks earlier.

### healthchecks.io — tested, and the answer was not what it looked like

The dead-man switch was never broken. Tested deliberately using the `fail` mode
already built into the `hc-ping` helper, which appends `/fail` and marks a check
down immediately instead of waiting out the grace period:

    sudo /usr/local/bin/hc-ping <check> fail    # alert
    sudo /usr/local/bin/hc-ping <check>         # resolve

All five — `backup-vault`, `backup-nas`, `backup-etcd`, `backup-cloud`,
`backup-verify` — alerted and resolved correctly.

**So it did fire on 04 Aug. It went to email, and email is not a channel that
gets watched.** Prometheus criticals go to ntfy and reach the phone within
seconds; healthchecks.io goes to email and effectively reaches nobody. The
failure was three days of invisible broken backups, and the cause was a working
alert delivered to the wrong place.

Note that `hc-ping ... fail` returning `OK` means **healthchecks.io accepted the
ping**, not that a notification was delivered. The two were checked separately —
inbox confirmed — because that distinction is the same one that made a green
`systemctl list-timers` look like a working offsite backup.

**Fix: attach the ntfy integration to every check** (Integrations → Add → ntfy in
the healthchecks.io UI). Integrations are attached *per check*, so adding it once
does not cover the others. While there, confirm each check's Period and Grace
match the values documented in `ansible/playbooks/healthchecks.yml` — those are
set by hand in the UI and nothing enforces the match.

**Gap: there is no healthchecks.io check for `backup-offsite`.**
`secret/lab/healthchecks` has no key for it. It is about to become the only copy
of the data that survives losing the H4, and it is currently the least monitored
thing in the lab.

## 🔁 The pattern worth remembering

Almost every fault here was invisible because another was masking it, and
several were reported green by checks that could not see the failure mode:

- the systemd collector was written off on a wrong diagnosis, and behind it sat a
  metric-name typo that would have kept the rules dead anyway
- kyverno's hook failed on a deleted image while the app reported Synced/Healthy
- `lab-check.sh` aborted before running its last two checks, and its restart
  warning only fired when there was nothing to report
- the `ldap-1` backup probe had been red since 18 July, which is why nobody
  noticed `lldap-backup` hang for 3d15h
- `backup-offsite` logs "Finished restic copy of the primary repo to OFFSITE"
  on runs where it copies nothing, because the skip path exits 0 and systemd
  prints the unit `Description=`

A health check that cannot go red is worse than no health check, because it
teaches you the output is noise.

The 08-05 immich bug is the same shape from the other side: a check that went red
while the thing it checked was **fine**, and deleted good output on the strength
of it. Both failures come from trusting an assertion nobody had watched fail.
Write the check, then make it fail on purpose and confirm it fails for the reason
you think.

The 08-05 evening lockout adds a third: **verify the replacement before
destroying the original.** The admin token was tested for *capability* — it could
write policies, enable auth methods, read secrets — but never for *independence*.
It was a child of the token about to be revoked, and no capability check would
ever have shown that. The right test is not "does the new credential work?" but
"does the new credential still work once the old one is gone?" — and the only way
to answer that safely is to know the dependency exists before you pull.

Two smaller ones from the same evening, both about privilege boundaries:

- `sudo cmd < file` and `sudo ls /root/glob*` do **not** work. Redirection and
  globbing happen in the calling shell, before sudo runs. The first leaked a
  Tier 1 secret into a transcript; the second sent us looking for a backup that
  had been created correctly all along.
- Check *which host* you are on before editing config. `/etc/vault.d/vault.hcl`
  exists on both the H4 and the RPi5; only one of them is running anything.

And the one this week kept returning to: **an alert that reaches a channel nobody
watches is indistinguishable from no alert at all.** healthchecks.io worked
perfectly for three days while backups were broken. Every layer did its job and
the outcome was identical to having no monitoring. When adding a check, the last
question is not "does it fire?" but "where does it land, and do I look there?"

And one about diagnosis: **identify the product before reading its docs.** Vault
2.0.3 and OpenBao 2.0.3 carry the same version number, and hours went into a
deprecation notice, a CVE, and a config parameter belonging to the wrong project.
`dpkg -l` / `apt policy` settles it in one command and should have been the first
thing run, not the last. The clue was there the whole time — the config key was
rejected as *unknown*, which means "wrong product", not "wrong placement".
