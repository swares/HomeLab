Started as "fix wifi and login on opi02w-4", became a fleet-wide audit of checks

All changes went through GitOps (PRs → ArgoCD sync) or Ansible playbooks.

## ✅ Completed

### opi-zero2w-4 rebuild

- [x] **Root cause was storage geometry, not wifi.** The ext4 filesystem claimed
  15,204,352 4K blocks while its partition held 15,203,266 — the filesystem
  extended ~4.2 MB past the end of the card. Every boot wrote past usable space,
  corrupting config and leaving the journal dirty. That is why credentials and
  NetworkManager state were broken, and why `e2fsck` refused to run.
  Fixed by growing the image file 16 MB, replaying the journal, `resize2fs` down
  to the true partition size, then truncating back.

- [x] **Original SD card failed** — stopped enumerating entirely afterwards
  (`Get-CimInstance` / `Get-Disk` / Disk Management all blind to it while the
  reader itself was healthy). Replaced.

- [x] **Rebuilt on Orange Pi OS Debian Bookworm, BSP kernel 6.1.31.** The board
  had been on Orange Pi OS *Arch* (`Opios-arch-aarch64-xfce`), a rolling distro
  pinned to a frozen out-of-tree kernel, with a desktop stack on a headless node.

  Armbian is **not** an option for this board: it publishes only `current`
  (6.18.x) images, and the Zero 2W's **UNISOC UWE5622** wifi has no mainline
  driver. Verified by mounting the Armbian image — no `uwe5622`/`sprdwl_ng`
  modules, no `wcnmodem.bin`. Flashing it would have produced a board with no
  network and no ethernet port to recover through.

- [x] **Orange Pi's first-run mechanism is dead on arrival.**
  `orangepi-firstrun.service` already ran on Xunlong's build machine
  (`2024-07-11`) and removed its own enablement symlink, so
  `/boot/orangepi_first_run.txt` is never read on the user's first boot. Any
  headless preconfiguration must write the NetworkManager keyfile directly.

- [x] Board now `opi-zero2w-4` at `192.168.1.99` (matches inventory and Pi-hole
  client list), wifi surviving reboots, mosquitto HA-bridged to `opi-zero2w-2`,
  node-exporter and promtail restored **from playbooks, not the salvage tarball**.

- [x] **Wifi powersave disabled fleet-wide on the Zero 2W pool.** The UWE5622
  defaults to powersave on, parking the radio and dropping the first packet after
  idle — boards showed as intermittently unreachable in `lab-check`.
  `opi-zero2w-1/2/4` via NetworkManager; `opi-zero2w-3` runs netplan +
  systemd-networkd + wpa_supplicant (the odd one out) and got a oneshot unit plus
  a udev rule. Baked into `tools/sdcard/prep-armbian.sh` for future boards.

- [x] **SD card tooling committed** to `tools/sdcard/`. Windows cannot
  `wsl --mount` removable media, and standard imagers enumerate drive letters
  rather than physical disks, so these do raw `\\.\PHYSICALDRIVEn` access:
  `Inspect-SDCard.ps1`, `Dump-SDCard.ps1`, `Write-SDCard.ps1`, `prep-armbian.sh`,
  `diag-opi.sh`.
  `Write-SDCard.ps1` locks/dismounts volumes via FSCTL (`Set-Disk -IsOffline`
  does not work on removable media) and verifies by SHA256 readback.

### Cluster outage — all 11 ArgoCD apps Degraded

- [x] **One expired Vault token.** The ESO `ClusterSecretStore/vault-backend`
  used a static token in `external-secrets/vault-token`; it expired, every
  `ExternalSecret` failed to refresh, and ArgoCD marked every app Degraded.

  **Zero workload impact** — ESO's default `deletionPolicy: Retain` left all
  previously-synced Secrets in place, so running pods never noticed. Confirmed:
  no pod restarted during the ~2h window.

  Fixed by minting a token with policy `eso` (`-period=768h`) and patching the
  Secret. Note the store is declared under `gitops/workloads/immich`, which is
  surprising.

- [x] **Two stale-CIDR pods from the `n150-2` rebuild.** `n150-2` was rebuilt
  5d21h prior and came back with pod CIDR `10.42.1.0/24`, but `promtail-kgskt`
  (`10.42.3.5`) and `svclb-traefik-...-zzwgk` (`10.42.3.2`) survived the API
  object across it, holding addresses from a subnet that no longer routes
  anywhere. Six days of no log shipping and no ingress from that node. Deleting
  the pods fixed both.

### Monitoring — systemd collector finally works

- [x] **The 2026-07-26 diagnosis was wrong.** It concluded the collector could
  not work because node_exporter reads `/run/systemd/private` (root-only) — so
  the capability was written off and backup liveness moved to healthchecks.io.
  The pod log names a different path: it wants the D-Bus **system bus** at
  `/var/run/dbus/system_bus_socket`, which is `srw-rw-rw-`. No root needed.

- [x] Mounting the socket fixed the two arm64 nodes but not the three Ubuntu
  ones, which then failed on **AppArmor** — containerd applies its default
  profile and dbus-daemon mediates by peer profile, refusing the `Hello`
  handshake. Orange Pi Jammy ships no AppArmor, hence the arch-looking split.
  Fixed with `appArmorProfile: Unconfined` on the container (UID 65534,
  `runAsNonRoot` and read-only rootfs all retained).

- [x] **The alert rules referenced a metric that does not exist.**
  `node_systemd_timer_last_trigger_TIME_seconds` — no `_time` in the real name.
  That misspelling was also documented as "known-absent" and used as evidence
  the collector was broken. Two faults stacked, each hiding the other.

- [x] **Every backup now has an alert behind it**, for the first time:
  - `backup-nas`, `backup-etcd` — systemd timers on `odroid-nas`
  - `backup-vault` — systemd timer on `rpi5` (its series existed all along under
    `job="node-exporter-external"`; no rule referenced it)
  - `lldap-backup`, `immich-db-backup` — CronJobs, via new `LabCronJobStale`

- [x] **`lldap-backup` hung for 3d15h** on an unreachable NFS mount (the restic
  repo is an inline `nfs:` volume from the NAS) with no `activeDeadlineSeconds`
  to bound it, and nothing alerting. Added `activeDeadlineSeconds: 1800` and
  `backoffLimit: 2`.

### kyverno — sync failed since 2026-07-22

- [x] **A PostSync hook pulling a deleted image.** `kyverno-clean-reports` wanted
  `docker.io/bitnami/kubectl:1.30.2`; Bitnami moved its free catalog to
  `docker.io/bitnamilegacy/*` on 2025-09-29. The Job sat in `ImagePullBackOff`,
  every full sync hung on it and failed — while the app reported `Synced/Healthy`
  throughout, because the Deployments were genuinely fine.
  Fixed via `webhooksCleanup.image.repository` and
  `policyReportsCleanup.image.repository`.

- [x] Documented that the pre-existing `cleanupJobs` registry override **targets
  nothing** — `kubectl -n kyverno get cronjob` is empty on chart 3.3.4. It was
  added for this same Bitnami problem, against the wrong values path.

- ⚠️ **`kubectl patch app <name> -p '{"operation":{"sync":{}}}'` drops
  `spec.syncPolicy.syncOptions`** and applies client-side. On kyverno that
  produces a completely misleading `metadata.annotations: Too long` error against
  the large CRDs. Trigger syncs from the UI/CLI, or include `syncOptions` in the
  patch. Also: clearing `.operation` directly orphans
  `argocd.argoproj.io/hook-finalizer` and wedges the app —
  `argocd app terminate-op` unwinds hooks properly.

### Checks that lied

- [x] **`lab-check.sh` aborted before its last two sections.** `set -euo
  pipefail` plus `x=$(cmd)` on commands that can legitimately fail — the script
  died at the Ollama section, so `Loop device (LVM backing)` and the final
  summary had **never run**. Worse, the aborts correlated with breakage: the
  Vault check killed the script if Vault was unreachable.

- [x] **Ollama check could never have passed.** It curled ollama's ClusterIP from
  the host, but `ai-gateway` has `default-deny-all` and ollama accepts traffic
  only from litellm. Replaced with Deployment readiness.

- [x] **High-restart warning ran only when there was nothing to warn about.**
  `... | grep -v 'svclb-' || true | while read ...` parses as
  `(pipeline) || (true | while ...)`, so when grep *found* something its output
  went to stdout unformatted and the loop was skipped. Two Alloy pods at 8
  restarts printed as bare text and never counted as warnings.

- [x] **`Synced/Healthy` cannot see a failed sync operation.** Added
  `.status.operationState.phase` to the ArgoCD section — kyverno was reported
  green for eleven days.

- [x] **Stale expectations retired**: `ldap-1` host entry and its
  `backup-lldap.timer` SSH probe (VM decommissioned 2026-07-18);
  `INGRESS_VIP` still `192.168.1.160` when `traefik-vip` moved to
  `192.168.1.201`; an orphaned `/etc/dnsmasq.d/10-lab-zone.conf` on octopi making

- [x] **`sync-secrets-to-vault.yml` had `delegate_to: ldap-1`** — the whole

### Ansible `--check` audit

- [x] **`command`/`shell` tasks skip under `--check`, so any register consumed by
  a later conditional misevaluates.** Found after `create-vm.yml` aborted a dry
  run claiming `example-1` already existed — a VM that has never existed.
  Audited all ~70 registers, split read-only probes from mutating tasks, and
  added `check_mode: false` to ten probes across eight files.

  `storage.yml` mattered most: `failed_when: loop_check.rc != 0` meant a dry run
  silently skipped verifying `/dev/loop100` was attached — and that loop device
  backs `vg_microshift`, i.e. every k8s PV.

  Mutating tasks deliberately left alone; their registers being empty under
  `--check` is correct.

- [x] **`create-vm.yml` defaulted `vm_name: ldap-1`.** A forgotten
  `-e vm_name=` would provision a VM named after a decommissioned host, and the
  existing "VM already exists" guard could not catch it — `virsh dominfo` returns
  not-found *because* the VM is gone. Default removed, assert added, and
  post-create tasks gated on `not ansible_check_mode`.

- [x] **`ansible.cfg`: `pipelining = True`.** Fixes `Module invocation had junk
  after the JSON data` on `opi-zero2w-2` — that was sftp's batch-mode `sftp> put`
  echo leaking into stdout, from an OpenSSH version mismatch between the Ubuntu
  22.04 control node and the newer Arch host. Also a fleet-wide speed-up.

## 🔁 The pattern worth remembering

Almost every fault here was invisible because another was masking it, and
several were reported green by checks that could not see the failure mode:

- the systemd collector was written off on a wrong diagnosis, and behind it sat a
  metric-name typo that would have kept the rules dead anyway
- kyverno's hook failed on a deleted image while the app reported Synced/Healthy
- `lab-check.sh` aborted before running its last two checks, and its restart
  warning only fired when there was nothing to report
- the `ldap-1` backup probe had been red since 18 July, which is why nobody
  noticed `lldap-backup` hang for 3d15h

A health check that cannot go red is worse than no health check, because it
teaches you the output is noise.
