## ✅ Completed

### opi-zero2w-4 rebuild

- [x] **Root cause was storage geometry, not wifi.** The ext4 filesystem claimed
  15,204,352 4K blocks while its partition held 15,203,266 — the filesystem
  extended ~4.2 MB past the end of the card. Every boot wrote past usable space,
  corrupting config and leaving the journal dirty. That is why credentials and
  NetworkManager state were broken, and why `e2fsck` refused to run.
  Fixed by growing the image file 16 MB, replaying the journal, `resize2fs` down
  to the true partition size, then truncating back.

- [x] **Original SD card failed** — stopped enumerating entirely afterwards
  (`Get-CimInstance` / `Get-Disk` / Disk Management all blind to it while the
  reader itself was healthy). Replaced.

- [x] **Rebuilt on Orange Pi OS Debian Bookworm, BSP kernel 6.1.31.** The board
  had been on Orange Pi OS *Arch* (`Opios-arch-aarch64-xfce`), a rolling distro
  pinned to a frozen out-of-tree kernel, with a desktop stack on a headless node.

  Armbian is **not** an option for this board: it publishes only `current`
  (6.18.x) images, and the Zero 2W's **UNISOC UWE5622** wifi has no mainline
  driver. Verified by mounting the Armbian image — no `uwe5622`/`sprdwl_ng`
  modules, no `wcnmodem.bin`. Flashing it would have produced a board with no
  network and no ethernet port to recover through.

- [x] **Orange Pi's first-run mechanism is dead on arrival.**
  `orangepi-firstrun.service` already ran on Xunlong's build machine
  (`2024-07-11`) and removed its own enablement symlink, so
  `/boot/orangepi_first_run.txt` is never read on the user's first boot. Any
  headless preconfiguration must write the NetworkManager keyfile directly.

- [x] Board now `opi-zero2w-4` at `192.168.1.99` (matches inventory and Pi-hole
  client list), wifi surviving reboots, mosquitto HA-bridged to `opi-zero2w-2`,
  node-exporter and promtail restored **from playbooks, not the salvage tarball**.

- [x] **Wifi powersave disabled fleet-wide on the Zero 2W pool.** The UWE5622
  defaults to powersave on, parking the radio and dropping the first packet after
  idle — boards showed as intermittently unreachable in `lab-check`.
  `opi-zero2w-1/2/4` via NetworkManager; `opi-zero2w-3` runs netplan +
  systemd-networkd + wpa_supplicant (the odd one out) and got a oneshot unit plus
  a udev rule. Baked into `tools/sdcard/prep-armbian.sh` for future boards.

- [x] **SD card tooling committed** to `tools/sdcard/`. Windows cannot
  `wsl --mount` removable media, and standard imagers enumerate drive letters
  rather than physical disks, so these do raw `\\.\PHYSICALDRIVEn` access:
  `Inspect-SDCard.ps1`, `Dump-SDCard.ps1`, `Write-SDCard.ps1`, `prep-armbian.sh`,
  `diag-opi.sh`.
  `Write-SDCard.ps1` locks/dismounts volumes via FSCTL (`Set-Disk -IsOffline`
  does not work on removable media) and verifies by SHA256 readback.

### ✅ Completed

- [x] **`lldap-backup` was installing restic at runtime.** The job ran
  `apk add --no-cache restic` inside `postgres:16-alpine` on every invocation, so
  each nightly backup depended on `dl-cdn.alpinelinux.org` being reachable over
  TLS at 02:30. On 04 Aug it was not:

      WARNING: fetching .../v3.24/main/aarch64/APKINDEX.tar.gz: TLS: unspecified error
      ERROR: unable to select packages:
        restic (no such package): required by: world[restic]

  restic was not missing from Alpine — the *package index* fetch failed, so apk
  had no catalogue. Exited non-zero twice, hit `backoffLimit` 64 seconds in, and
  that night's snapshot was lost. Not reproducible on a manual run hours later,
  because the CDN was reachable again by then.

  Split into two stock images with nothing fetched at runtime:
  `initContainer pg-dump` (`postgres:16-alpine`) →
  `container restic-backup` (`restic/restic:0.17.3`, verified on arm64), handing
  the dump over via an `emptyDir`.
  `gitops/workloads/lldap/backup-cronjob.yaml`
  *(PR `fix/lldap-backup-no-runtime-install`)*

  Side benefit: the content assertions (>1000 bytes, contains `CREATE TABLE`)
  now live in the init container, so a bad dump means the restic container never
  runs and cannot reach the repository. Previously only shell ordering prevented
  that.

      Flag --last has been deprecated, use --latest 1
      Ignoring "filters": explicit snapshot ids are given

  The backup was fine; its own summary was lying. Now `--latest 5`. Note
  `--latest N` shows N *per group* (host+paths), so output stays longer than

### 🔎 Loki access notes

Grafana Explore is the practical route: `https://grafana.apps.lab.home.arpa` →

  cluster pods    job="loki.source.kubernetes.pods"   namespace / pod / container

## 2026-08-05 — immich consolidation, and OpenBao reconnaissance

### ✅ immich backup consolidation

One asserted, pruned backup path. **847 MB → 255 MB.**

- Built-in Immich backup **disabled** in the admin UI. Its schedule and
  `keepLastAmount` live in Immich's own database and are settable only through
  that UI — they cannot be reviewed, version-controlled, or restored with the
  rest of the lab, which is the whole reason the GitOps CronJob wins. If the
  built-in is ever preferred, manage it declaratively via `IMMICH_CONFIG_FILE`
  rather than re-enabling it by hand.
- 14 leftover `immich-db-backup-*.sql.gz` files removed (227 MB). The CronJob's
  retention glob is deliberately strict (`immich-????-??-??.sql.gz`) so it will
  never touch the built-in's filenames — a bare `immich-*` would have.
- CronJob moved 01:30 → **01:00**, ahead of `backup-nas` at 01:30, plus atomic
  `.tmp` + `mv`, size assertion, `gzip -t`, a CREATE TABLE assertion, and 14-day
  retention. First real run: 24 dumps pruned, 16 retained.

**The bug worth remembering — `set -o pipefail` plus an early-exiting consumer.**
The content assertion was written `zcat "$TMP" | grep -q 'CREATE TABLE'`. That
is wrong in a way that only appears at scale: `grep -q` exits on the *first*
match, the decompressor is still writing ~208 MB, it takes SIGPIPE and exits
141, and `pipefail` promotes that to a failure of the whole pipeline. So a
**passing** check reported failure, and the job deleted a perfectly good dump.
Reproduced at the same scale — `grep -q` → rc=141, `grep -c` → passes. `grep -c`
reads the whole stream, so there is no early close. The same trap applies to the
`ls | head -20` line, which needs `|| true`.

Three days of dumps were lost to this before it was caught. Nothing at risk —
the failure path only ever removed `$TMP` — but the *backup was not running*
while the CronJob reported a clean, deliberate-looking error message.

**And a lesson about my own diagnosis:** after the `grep -q` fix was merged, jobs
kept failing, so I built two further theories (a missing `zcat`, then a mismatched
image) and had the user run probes against both. Both were wrong. The jobs that
kept failing were *pre-merge runs* — I never pinned the merge time against the job
timestamps, so I was explaining stale evidence with new hypotheses. Checking what
was actually deployed took one command and ended it immediately:

    kubectl -n immich get cronjob immich-db-backup \
      -o jsonpath='{.spec.jobTemplate.spec.template.spec.containers[0].args[0]}'

Establish *which version produced the failure* before theorising about why.

### 🔑 OpenBao root token — reconnaissance complete, nothing revoked yet

The exposed init root token **is still live**. Confirmed identity:
`display_name root`, `path auth/token/root`, `policies [root]`, no expiry.

Seal state: **shamir, 5 shares, threshold 3**, and all five shares are
retrievable — so `operator generate-root` is a working recovery path and none of
this is one-way.

Three tokens exist in total:

    auth/token/root      root                      [root]          no expiry   <- exposed
    auth/token/create    token-eso                 [default eso]   2026-09-01
    auth/token/create    token-root-replacement    [root]          no expiry

The **second root token changes the plan**. The original intent was to migrate
ESO first so one root session covered both jobs; but since `token-root-replacement`
already holds root, the exposure can be closed immediately rather than after a
multi-hour migration. Order:

1. **Revoke the exposed token** — no key ceremony needed
2. ESO → Kubernetes auth, using the replacement
3. Create an `admin` policy + TTL-bounded token
4. Revoke `token-root-replacement` → **zero standing root**

**The one unverified step, and where to resume:** nobody has yet authenticated as
`token-root-replacement`. If it was created in a shell and never saved, it is
unusable, and revoking the exposed token would force a `generate-root` ceremony.
Prove it first — this also sidesteps the self-revocation trap, where you revoke
the token your own session is using:

    vault token lookup | grep -E '^(display_name|path)'   # which am I using?
    vault login                                            # paste at the prompt, not argv
    vault token lookup | grep display_name                 # expect token-root-replacement
    vault token revoke -accessor <exposed-accessor>
    vault token lookup -accessor <exposed-accessor>        # expect: invalid accessor

Then confirm nothing was quietly depending on it — `backup-vault` especially, in
case its snapshot credential was ever the init root token rather than the
`vault-snapshot` policy.

Expected blast radius: none. ESO holds its own `[default eso]` token, and
`deletionPolicy: Retain` means even a total Vault outage leaves running workloads
untouched — established during the July degradation.

`token-root-replacement` also tells a story: a rotation was started at some point
and never finished, leaving *two* non-expiring root tokens. Step 4 is what
actually closes it.

**Hard deadline:** the ESO token expires **2026-09-01**. That is four weeks from
now and is a real outage date, not a nice-to-have. The 2026-08-24 reminder is the
fallback to rotate the static token if the auth migration has not landed.

### 🔴 `backup-offsite` has never copied anything

Found while mapping which repos the leaked password covers. **The NAS data has no
offsite copy and has not had one since the unit was written.**

`ansible/playbooks/backup.yml:19` sets
`restic_offsite_repo: "{{ offsite_restic_repo | default('') }}"`, and
`offsite_restic_repo` is defined **nowhere** — not in inventory, not in
group_vars, nowhere in the repo. The template handles empty by design:

    test -n "" || { echo "no offsite repo configured; skipping"; exit 0; }

So the unit exits 0 and the timer reports `PASSED`. Confirmed in the journal:

    Aug 05 02:30:00 bash[2601613]: no offsite repo configured; skipping
    Aug 05 02:30:00 systemd[1]: Finished restic copy of the primary repo to OFFSITE (3-2-1).

**The `Description=` makes the skip look like a success.** The journal literally
says it finished copying to offsite, on the run where it copied nothing. This was
already flagged in `TODO-2026-07-23.md:133` and `RUNBOOK.md:162` as wired-but-unset
— it was then mistaken (by me, 08-05) for working protection on the strength of a
green `systemctl list-timers`.

Consequence: 203 GiB of NAS data exists as two mirrors **in the same chassis** —
the single failure domain CLAUDE.md warns about. `backup-cloud` (03:00 → R2) does
run, but it carries *cluster state* only: etcd + Vault snapshots, lldap, and the
Authelia/Immich/Semaphore dumps. Fire, theft, or a PSU that takes both SATA disks
loses the data outright.

Fix: set `offsite_restic_repo` in group_vars and provide `/etc/restic/offsite.env`.
Consider making the skip path fail, or at least warn — a no-op that logs "Finished"
is worse than an unconfigured unit that refuses to start.

### 🔑 restic repository password exposed — ✅ ROTATED 2026-08-05 20:43 UTC

The password from `/etc/restic/password` was printed into a chat transcript on
08-05. Cause was a broken privilege boundary in a command intended to compare it
*without* disclosure:

    sudo tr -d '\n' < /etc/restic/password    # WRONG

The `<` redirection is performed by the calling shell, not by sudo, so the read
failed with permission denied, the left side of the `diff` was empty, and diff
printed the Vault copy in full as an addition. Correct form:

    sudo cat /etc/restic/password | tr -d '\n' | sha256sum

**Scope — two repos, both local:**

    /mnt/cold-8t/restic     primary       AFFECTED
    /mnt/cold-sec/restic    copy          AFFECTED
    s3:...r2.../homelab-backup   cloud    NOT affected — separate password,
                                          /etc/restic/cloud-password from
                                          secret/lab/cloudflare-r2

Rotation is cheap: a restic password protects the master key, not the data, so
this re-encrypts kilobytes rather than 203 GiB. `key add` / `key remove` is not
`forget`/`prune` and does not touch snapshots or retention.

    restic -r <repo> key list
    restic -r <repo> key add          # both repos
    # verify new password against BOTH before removing anything
    restic -r <repo> key remove <old-id>

Then update `/etc/restic/password`, `secret/lab/restic`, and the offline copy.
Confirm the lldap backup CronJob still runs afterward — it reads
`RESTIC_PASSWORD_FILE=/secrets/restic-password`, which comes from
`secret/lab/restic` via ESO, so a missed propagation surfaces at 02:30.

Note the `/etc/restic/password` file ends with a newline and the Vault copy does
not. Same password — restic trims it — but it means a `sha256sum` of the *file*
will not match a hash of the stored string. Compare trimmed values.

**Outcome.** Both repos now hold exactly one key:

    /mnt/cold-8t/restic   (4154928a)   44f892c5  created 20:43:01
    /mnt/cold-sec/restic  (34b4735f)   46108177  created 20:35:44

Removed: `87ff5770` and `4aead2b2` (the exposed June keys, one per repo) and
`75f20474` — a **stray third key** on the primary from a re-run of `key add` at
20:34, whose password was not retained. Removing it mattered: an unknown
credential on the copy-of-record is a loose end even when it isn't a known
exposure. Worth remembering that `restic key add` appends unconditionally, so a
mistyped confirmation leaves a working key behind with no warning — always
`key list` before `key remove`, and never remove the row marked `*`.

Verification, in order: both repos opened with the new password before anything
was removed; `secret/lab/restic` updated (now version 5); both `lldap-*`
ExternalSecrets showed `SecretSynced` and were force-annotated; then
`backup-verify` was run manually at 20:52 and passed — `restic check clean` on
`/mnt/cold-8t/restic`, `/mnt/cold-sec/restic`, **and** R2. Only then were the old
keys removed and `/etc/restic/password.old` shredded.

Still to confirm on the morning of 08-06 — the first *unattended* runs against
the new password, one per consumer path:

    backup-nas       01:30 UTC   reads /etc/restic/password (file)
    lldap-backup     02:30 UTC   reads the ESO-delivered k8s secret (Vault)

The manual `backup-verify` covers the file path; the CronJob is the only thing
that exercises the Vault → ESO → secret chain end to end.

## 🔁 The pattern worth remembering

Almost every fault here was invisible because another was masking it, and
several were reported green by checks that could not see the failure mode:

- the systemd collector was written off on a wrong diagnosis, and behind it sat a
  metric-name typo that would have kept the rules dead anyway
- kyverno's hook failed on a deleted image while the app reported Synced/Healthy
- `lab-check.sh` aborted before running its last two checks, and its restart
  warning only fired when there was nothing to report
- the `ldap-1` backup probe had been red since 18 July, which is why nobody
  noticed `lldap-backup` hang for 3d15h
- `backup-offsite` logs "Finished restic copy of the primary repo to OFFSITE"
  on runs where it copies nothing, because the skip path exits 0 and systemd
  prints the unit `Description=`

A health check that cannot go red is worse than no health check, because it
teaches you the output is noise.

The 08-05 immich bug is the same shape from the other side: a check that went red
while the thing it checked was **fine**, and deleted good output on the strength
of it. Both failures come from trusting an assertion nobody had watched fail.
Write the check, then make it fail on purpose and confirm it fails for the reason
you think.
